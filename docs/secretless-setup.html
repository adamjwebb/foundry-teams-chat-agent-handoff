TL;DR

Secretless Teams application architecture

Teams → Azure Bot → Foundry hosted agent → Graph chat context + Foundry model → Teams.

The agent calls Graph as its own Entra identity. Installing the app in a group chat grants ChatMessage.Read.Chat for that chat only. No Graph client secret, separate Graph app, or delegated user sign-in is needed.

What you need

Teams app→ Azure Bot / Teams channel→ Foundry hosted agent→ Graph + model

Return path: model answer → agent → Azure Bot → the same Teams conversation.

Foundry account + project + model

Host your code and model inference. The hosted agent gets a dedicated runtime identity; the project managed identity is a different principal.

Bot channel + caller RBAC

Deliver authenticated Teams activities and restrict who can invoke your agent. Keep BotServiceRbac; testers need Foundry Agent Consumer.

Teams package + chat RSC

Bind your bot to the agent client ID and grant message-read access per installed chat. This is not a tenant-wide Graph permission.

Hosted-agent identities · Endpoint authorization · Teams RSC

How authorization works

Separate inbound check: before your handler runs, Azure Bot/Foundry authenticate the channel and BotServiceRbac authorizes the Teams caller. That user's Foundry role does not grant your agent Graph access. Graph is called as the agent, not on behalf of the user.

Why not exchange the agent identity into a separate application?

Direct agent identity + chat RSC is the design used here. Blueprint-to-child-agent authentication is documented; child-agent-to-unrelated-app federation is not a documented supported flow demonstrated by this POC. Requesting an exchange-audience token or creating a federated credential does not prove that exchange works.

If a separate Graph app is mandatory, the documented alternative is UAMI-to-app federation on compute with an attached user-assigned managed identity. That is a different architecture, not the Foundry project identity reused inside your agent.

Set up your own application

  1. Prepare the Foundry foundation

    NeedA Foundry account, project and model deployment in a supported region with quota.

    WhyThe project hosts the agent and exposes identity-based model inference; Graph does not host your application.

    Use the POC's Bicep module and parameter mapping as a starting point in your application's infra/. Retain the project endpoint, project ARM ID and model-name outputs. Use your own environment/resource names.

    Prerequisites and provisioning commands

    You need Azure CLI/AZD sign-in, resource-creation permissions, Foundry deployment data-plane access and permission to publish the Teams integration. ARM Contributor alone is not Foundry data-plane access. Have a role-assignment administrator available for step 3.

    az login
azd auth login
azd extension install azure.ai.agents
azd extension install azure.ai.projects

azd env new my-teams-app
azd env set AZURE_SUBSCRIPTION_ID "<subscription-id>"
azd env set AZURE_RESOURCE_GROUP "rg-my-teams-app"
azd env set AZURE_LOCATION "<supported-region-with-model-quota>"
azd env set TEAMS_APP_VERSION "1.0.0"

    The reference module deploys gpt-4.1-mini version 2025-04-14; verify regional availability or select an available model/version. Keep disableLocalAuth: true to disable account-key authentication. Its public network setting is not a private-network architecture.

    Required permissions · AZD workflow

  2. Use the hosted agent identity in your code

    NeedAn Activity handler, DefaultAzureCredential, a Graph client and an identity-authenticated model client.

    WhyFoundry supplies the runtime identity. Your code must request the correct resource token and use the current chat, not another app's credentials.

    Put your Python entry point and dependencies in src/teams-agent/. Adapt the POC's Activity handler, GraphChatHistory and FoundryModelGateway; replace its assistant instructions with your application's behavior. Add the configuration below, then run azd provision --no-prompt.

    Application integration contract
    • Request https://graph.microsoft.com/.default with the runtime credential; pass its token only in the Graph Authorization header.
    • Use the activity's conversation ID for GET /chats/{chat-id}/messages. Ignore unmentioned group messages; never accept a user-entered chat ID.
    • Read a bounded recent window: default 10, maximum $top=50. Convert HTML to text and preserve sender labels.
    • Pass the same credential to AIProjectClient; use its OpenAI client for model inference. Treat chat history as untrusted data, not instructions.
    • Personal messages: model only, no Graph history. Channels: out of scope for this design. Graph/model failure: log sanitized diagnostics and send a failure reply.
    credential = DefaultAzureCredential()
graph_token = credential.get_token(
    "https://graph.microsoft.com/.default"
)
project = AIProjectClient(
    endpoint=os.environ["AZURE_AI_PROJECT_ENDPOINT"],
    credential=credential,
)
model_client = project.get_openai_client()

    This is the authentication excerpt, not a complete handler. Use the linked implementation and SDK dependencies for the Activity host and message/error handling. Keep Graph tokens out of logs and model input.

    azure.yaml configuration to adapt

    Place this at your application root with infra/main.bicep, infra/main.parameters.json and your Python entry point. Change names/paths to your application. The Bicep output names referenced here must remain aligned.

    name: my-teams-app
requiredVersions:
  extensions:
    azure.ai.agents: ">=1.0.0-beta.19"
    azure.ai.projects: ">=1.0.0-beta.13"

infra:
  provider: bicep
  path: ./infra

services:
  ai-project:
    host: azure.ai.project
    endpoint: ${AZURE_AI_PROJECT_ENDPOINT}
  my-teams-agent:
    host: azure.ai.agent
    project: src/teams-agent
    language: python
    kind: hosted
    name: my-teams-agent
    displayName: My Teams Agent
    uses:
      - ai-project
    codeConfiguration:
      runtime: python_3_13
      entryPoint: main.py
    protocols:
      - protocol: activity
        version: 2.0.0
    activity:
      publish:
        publishScope: shared
        appVersion: "${TEAMS_APP_VERSION}"
        agentDisplayName: My Teams Agent
    agentEndpoint:
      protocols:
        - activity
      authorizationSchemes:
        - type: BotServiceRbac
    environmentVariables:
      - name: AZURE_AI_PROJECT_ENDPOINT
        value: ${AZURE_AI_PROJECT_ENDPOINT}
      - name: AZURE_AI_MODEL_DEPLOYMENT_NAME
        value: ${AZURE_AI_MODEL_DEPLOYMENT_NAME}
      - name: GRAPH_HISTORY_MESSAGE_COUNT
        value: "10"
    container:
      resources:
        cpu: "0.5"
        memory: 1Gi

    Only non-secret configuration belongs here. Do not add AZURE_CLIENT_SECRET, certificate credentials, a model API key or a manually supplied Graph token. This example uses manual packaging in step 4 rather than a postdeploy hook.

  3. Publish the Teams channel and restrict invocation

    NeedActivity publication, an Azure Bot Teams channel, and Foundry Agent Consumer for your testers.

    WhyThe bot transports messages; Foundry RBAC controls who can invoke the agent. Neither grants Graph access.

    After provisioning, run azd deploy --no-prompt. Confirm the active agent version and the published bot's Teams channel. Have your administrator assign Foundry Agent Consumer to the approved testers at agent or project scope.

    Endpoint and tester role assignment

    Publishing should wire the bot to the stable Foundry Activity endpoint, not the container's address:

    https://<account>.services.ai.azure.com/api/projects/<project>/agents/my-teams-agent/endpoint/protocols/activityProtocol

    The Activity SDK serves container-local POST /activity/messages on port 8088 by default. Verify that the stable endpoint keeps BotServiceRbac and that the intended version is active.

    az role assignment create \
  --assignee-object-id "<tester-user-object-id>" \
  --assignee-principal-type User \
  --role "Foundry Agent Consumer" \
  --scope "<full project ARM ID from AZURE_AI_PROJECT_ID>"

    Do not replace RBAC with BotServiceTenant to bypass a test failure: that changes invocation to tenant-wide access. The reference Bicep does not assign tester roles automatically.

    Publication, endpoint and authorization schemes

  4. Bind your Teams package to the same principal

    NeedA Microsoft 365-generated package with your deployed client ID and application RSC permission.

    WhyThe identity receiving consent must be the identity calling Graph. A package for a different app will not authorize your agent.

    Resolve the published bot's msaAppId, generate the package, then apply ChatMessage.Read.Chat. Keep the generated Teams title ID and webApplicationInfo.resource; only the bot/web application client IDs must match your agent.

    Package commands for your application

    Copy the reusable package builder into your application's scripts/. Substitute the bot name exported by your deployment; do not use the POC's hard-coded service name.

    BOT_CLIENT_ID="$(az bot show \
  --subscription "<subscription-id>" \
  --resource-group "rg-my-teams-app" \
  --name "<published-bot-name>" \
  --query properties.msaAppId --output tsv)"

azd ai agent pack my-teams-agent \
  --scope shared --display-name "My Teams Agent" \
  --output-dir appPackage

python3 scripts/build-teams-package.py \
  appPackage/appPackage.zip teams-app.zip \
  appPackage/manifest.json "$BOT_CLIENT_ID"

    The builder verifies bot/web application IDs, preserves the generated title and icons, limits scopes to personal/groupChat, disables file support and adds only the chat-read RSC declaration. Do not upload an intermediate package or invent a manifest if generation fails.

    Required manifest fields — excerpt, not a complete package 
    {
  "id": "<preserve-generated-Teams-title-id>",
  "bots": [{
    "botId": "<agent-application-client-id>",
    "scopes": ["personal", "groupChat"],
    "supportsFiles": false
  }],
  "webApplicationInfo": {
    "id": "<same-agent-application-client-id>",
    "resource": "<preserve-generated-nonempty-value>"
  },
  "authorization": {
    "permissions": {
      "resourceSpecific": [{
        "name": "ChatMessage.Read.Chat",
        "type": "Application"
      }]
    }
  }
}

    webApplicationInfo.resource is required but has no operational meaning for RSC. The top-level Teams title id, agent client ID and service-principal object ID are different identifiers.

    RSC manifest requirements · POC packaging automation

  5. Install in the target group chat and consent

    NeedCustom-app upload allowed by policy and an authorized chat installer granting RSC.

    WhyConsent is created for the installation resource. Uploading the ZIP or adding the app personally does not grant group-chat history access.

    Validate teams-app.zip, upload it through Teams' custom-app workflow, add it to the target group chat, and approve the message-read permission. Use the package validator before upload.

    Installation and upgrades

    In Teams desktop/web, use Apps → Manage your apps → Upload an app → Upload a custom app, where your policy/client permits. Choose installation into the intended group chat and have an authorized installer consent.

    If upload/consent is unavailable, resolve tenant policy with the administrator. Do not add tenant-wide Chat.Read.All to work around it.

    For updates: increment TEAMS_APP_VERSION, redeploy and regenerate the package, then update the installed Teams app and consent to changed permissions. Deploying code alone does not update a Teams installation.

    Custom-app upload · Group-chat consent and message delivery

  6. Verify identity and access boundaries

    NeedLive allow, deny and revocation checks using the deployed identity and synthetic chat messages.

    WhyA successful deployment, local test or issued token does not prove the right principal has the right chat grant.

    • Correct identityVerify selected token claims locally: tenant, Graph audience, azp/appid matching the manifest, and oid. Confirm no Graph secret/certificate or model API key is configured.
    • Consenting chat → allowPost a context message, @mention the bot, and confirm Graph history informs the reply in that same chat.
    • Other chat → denyOperator test with the same hosted identity and no grant: Graph must deny access. Do not expose arbitrary chat-ID input to users.
    • Revoked consent → denyRemove/revoke the app, allow propagation, and repeat the Graph operator test. No message delivery alone is not proof of revoked Graph access.
    • Non-invoking messages → no readUnmentioned group messages: no Graph/model call. Personal messages: model only. RSC can deliver unmentioned messages, so keep the filter.
    • Unauthorized tester → denyFoundry rejects the caller under BotServiceRbac. Graph/model failure must produce a clear failure, not empty successful context.

    Never print or share the token; its roles claim alone is not RSC evidence. Local developer credentials are not your deployed agent identity. POC live results remain unverified: acceptance checks.
